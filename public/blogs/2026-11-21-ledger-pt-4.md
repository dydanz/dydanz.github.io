*Part 4 of **Money Doesn't Retry: Building a Ledger That Can't Lie**: idempotency and concurrency, or how a ledger tells "again" apart from "another".*

---

Back to the tunnel, one last time.

Rina taps **Top up**. The train goes underground. The app says "Something went wrong." The train comes out, she gets her signal back, and she taps **Top up** again.

From the ledger's side, two requests arrived, each saying "add Rp100,000 to Rina's wallet." Maybe the first one never got through. Maybe it got through, the money moved, and only the reply was lost in the tunnel. The two requests look the same.

The ledger has to decide: is this the same top-up asked twice, or is Rina topping up twice? Get it wrong one way and she's charged Rp200,000. Get it wrong the other way and a real second top-up is ignored.

The ledger can't tell from the request alone. It needs Rina's app to tell it, and that's the first half of this post. The second half is about a different kind of "twice": two requests for the *same money* arriving at the same moment.

---

## The cloakroom ticket

You hand your coat in at a theatre cloakroom and get ticket **#47**. After the show you hand the ticket back and get your coat.

Now suppose you lose track and go back to the counter a second time with the same ticket. The attendant doesn't hand you a second coat. They look at #47 and say "already collected." The ticket makes asking twice harmless.

Three details make the ticket work:

1. **You get the ticket before anything happens.** It's issued when the coat goes in, not when you come back.
2. **The number means one specific coat.** If you came back with #47 and asked for a red umbrella instead, the attendant wouldn't just hand one over. Something is wrong.
3. **The cloakroom keeps a list.** Without the list, the number is meaningless.

An **idempotency key** is that ticket. (Idempotent is a maths word for "doing it twice has the same effect as doing it once.") Every request that moves money carries one, in a header:

```http
POST /internal/v1/accounts/{account_id}/credits
Idempotency-Key: topup-7f3a9c
```

The important part is *who* creates it. Rina's app makes the key **when she starts the top-up**, before the first tap is sent. The first attempt and every retry of that top-up carry the same key. A genuinely new top-up gets a new one.

If the server created the key instead, the key would travel back in the reply. Rina's reply was exactly the thing that got lost in the tunnel. A ticket you never received can't protect you.

---

## Four answers to a repeated question

When a request arrives with a key the ledger has seen before, it has four possible answers. These are the actual rules, in plain words:

| What arrives | What the ledger says |
| :--- | :--- |
| A key it has never seen | "New request." Process it normally. |
| A known key, same request, already finished | "Here's what happened last time." The original reply, word for word. |
| A known key, same request, still being worked on | "I'm on it, ask again in a second." (`409`) |
| A known key, **different** request | "That ticket is for a different coat." (`422`) |

The second row is the one that saves Rina. Her retry gets back the exact reply the first attempt would have received. Same transaction id, same balance, plus a header saying `Idempotent-Replayed: true` so the app knows. No second top-up.

The last row is the one people forget. If the same key arrives with a different amount, the ledger refuses. That situation is never innocent. It means a client has a bug that's reusing keys, and quietly treating it as either "a replay" or "a new payment" would hide that bug and get the money wrong.

One more rule is easy to get wrong: **failures are replayed too.** If Rina's debit failed with `insufficient_funds`, asking again with the same key returns the same `insufficient_funds`. It doesn't try again. The answer to that request is final. If she tops up and wants to try the payment again, that's a new attempt with a new key.

## How it's built

### The ticket stub: one row per key

The cloakroom's list is a table:

```sql
CREATE TABLE ledger.idempotency_keys (
  client_id        TEXT     NOT NULL,
  key_hash         CHAR(64) NOT NULL,
  request_fingerprint CHAR(64) NOT NULL,
  operation        TEXT     NOT NULL,
  resource_id      UUID     NOT NULL,
  response_status  SMALLINT,  -- NULL in flight
  response_body    BYTEA,     -- exact bytes
  expires_at       TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (client_id, key_hash)
);
```

A few choices in there matter:

- **The key belongs to a client.** The primary key is `(client_id, key_hash)`, so two different callers who happen to pick the same key string never collide.
- **The raw key is never stored**, only its SHA-256 hash, and the key is never logged. A key can carry information about the payment, and nobody needs to read it back.
- **The reply is stored as raw bytes**, not as JSON. Postgres's JSON type would reorder the fields, and the promise is a byte-for-byte replay.
- **`response_status` is empty while the request is in flight.** That's how the ledger tells "finished" from "still working on it" (the `409` row).

### The fingerprint: what "same request" means

How does the ledger decide two requests are "the same"? It computes a **fingerprint**: a hash of the operation, the target account and the body.

The body is turned into *canonical* JSON first, with sorted keys and no extra whitespace. Otherwise `{"amount":100,"currency":"IDR"}` and `{ "currency": "IDR", "amount": 100 }` would get different fingerprints, and an innocent retry from a different library version would be refused as a "different coat." (Code here and below is lightly reformatted to fit the page.)

```go
// Fingerprint: SHA-256 of the operation, the
// target (e.g. the account id in the path) and
// the canonical JSON of fields.
func Fingerprint(
    op, target string, fields any,
) (string, error) {
    canon, err := canonicalJSON(fields)
    if err != nil {
        return "", err
    }
    h := sha256.New()
    fmt.Fprintf(h, "%s\x00%s\x00", op, target)
    h.Write(canon)
    return hex.EncodeToString(h.Sum(nil)), nil
}
```

Numbers are kept exactly as written, so a large amount isn't rounded through a floating-point value on the way. Part 2 explained why money is never a float, and that applies here too.

### Claiming the key: the database decides

In Part 3 I described the two steps every write goes through: **Tx1** records the request as PENDING, and **Tx2** does the work. The key is claimed *inside Tx1*, in the same commit that creates the transaction:

```
Tx1
  INSERT idempotency_keys ...
    ON CONFLICT DO NOTHING
    conflict? -> read the existing row:
                 replay / 409 / 422
  INSERT transactions (status = PENDING)
  INSERT events TransactionRequested
COMMIT
```

`ON CONFLICT DO NOTHING` is the whole trick. If two copies of Rina's request arrive at the same instant, both try to insert the same primary key. Postgres lets exactly one of them in, and the other finds a conflict and reads the row instead. No application code decides who was first. The database's uniqueness rule does, and it can't be raced.

Because the key and the PENDING transaction commit together, there's no moment where one exists without the other. That's what makes Part 1's database-kill drill come out clean: every retry with an original key found either nothing (start fresh) or its own transaction (replay or finish it).

There's also a Redis cache in front, holding finished replies so a retry can be answered without touching Postgres. It's only a shortcut. If Redis is down or gives a strange answer, the request carries on to Postgres, and Postgres decides. A cache that's allowed to say "no, this is new" would be a second source of truth, and Part 3 was about why you only get one.

### Proving it

The test fires **50 requests at once, all with the same key**, to credit Rp7:

- exactly **1** transaction exists afterwards
- the balance is **7**, not 350
- every one of the 50 callers got either the identical reply or a `409` "still working on it"

## The other kind of twice

Idempotency handles *the same request* arriving twice. It does nothing for two *different* requests that want the same money.

Say Rina has Rp50,000 left. At 12:00:00 she pays Rp50,000 for lunch, and at the same moment her streaming subscription tries to renew for Rp30,000. Two different payments, with different keys, both legitimate. Only one of them can succeed.

Here's what happens if the ledger isn't careful. Both requests run at the same time:

```
  lunch (50,000)            subscription (30,000)
  --------------            ---------------------
  read balance: 50,000
                            read balance: 50,000
  50,000 >= 50,000? yes
                            50,000 >= 30,000? yes
  write balance: 0
                            write balance: 20,000
```

Both checks passed, because each one looked at a balance the other was about to change. Rina spent Rp80,000 out of Rp50,000, and her balance says Rp20,000. This is called a **lost update**, and it's the classic double-spend.

The fix is the same as at a shop counter with one ledger book: **one person at a time holds the pen.**

```sql
SELECT ... FROM ledgers
 WHERE account_id = $acct AND currency = $cur
   FOR UPDATE
```

`FOR UPDATE` locks that ledger row. The second payment waits at that line until the first one commits, then reads the *new* balance, Rp0, and fails with `insufficient_funds`. No cleverness, just waiting in line.

The test for this: an account with Rp1,000, and **200 debits of Rp10 fired at once**.

- exactly **100** succeeded and **100** failed with `insufficient_funds`
- the final balance is exactly **0**
- the journal has 101 lines (the opening credit plus 100 debits), numbered with no gaps, and every line's running balance matches the sum of the lines before it

There's also a `CHECK` constraint on the table that forbids a negative balance, as a last line of defence. In a correct system it never fires. It's there for the day the system isn't correct.

## Waiting in line without getting stuck

Locks bring their own way to fail: a **deadlock**. Two people at a dinner table each need a knife and a fork. One picks up the knife, the other picks up the fork, and each waits forever for the other to put theirs down.

In a ledger, that's two transactions each holding one row lock and waiting for the other's. Postgres detects it and kills one, which is a failed payment for no good reason.

The rule that prevents it is boring and absolute: **every code path takes its locks in the same order.**

```
1. the transaction row  (FOR UPDATE)
2. the account row      (FOR SHARE;
                         FOR UPDATE to freeze)
3. the user's ledger    (FOR UPDATE)
4. [void only] the original transaction
```

If everyone picks up the knife before the fork, nobody can be holding the fork while waiting for the knife. Each request touches exactly one user ledger, and the shared system ledgers from Part 2 are never locked at all, so they can't become a bottleneck either.

Notice the account row in step 2. Ordinary payments take it **shared**: any number of them can hold it at once, since they only need to check that the account isn't frozen. A **freeze**, the fraud team's emergency brake, takes it **exclusively**. It has to wait for the payments in progress to finish, and then every later payment sees `FROZEN`.

That was the design, anyway.

## When it broke: the freeze that couldn't get in

Picture a door with a sign that says "Shared, or one person alone." People with shared passes can walk in together. A person who needs the room alone has to wait until it's empty.

Now picture a steady stream of shared-pass holders. The room is never empty, because a new one walks in before the last one leaves. The person waiting to be alone waits forever.

That's what I found in Postgres 17 while testing the freeze. When a `FOR UPDATE` request is waiting on a row, a *new* `FOR SHARE` request can still be granted, as long as it's compatible with the locks already held. Row locks don't form a fair queue.

So under steady payment traffic on one account, each new payment could take its shared lock ahead of the waiting freeze, and the freeze could sit there until its timeout expired. And when is an account under steady payment traffic? During exactly the fraud burst the freeze was meant to stop.

The fix uses a different kind of lock. Postgres **advisory locks** are queued strictly in arrival order. So before touching the account row, every path first takes an advisory lock on the account, shared for payments and exclusive for a freeze:

```go
func (q ledgerQueries) lockAccount(
    ctx context.Context, id string, mode LockMode,
) (AccountRecord, error) {
    lock := "FOR SHARE"
    adv := "pg_advisory_xact_lock_shared"
    if mode == LockUpdate {
        lock = "FOR UPDATE"
        adv = "pg_advisory_xact_lock"
    }
    // 1. Queue fairly: advisory locks are
    //    granted in arrival order.
    _, err := q.db.Exec(ctx, `SELECT `+adv+
        `(hashtextextended(`+
        `'ledger.account:' || $1::text, 0))`, id)
    if err != nil {
        return AccountRecord{},
            fmt.Errorf("lock account: %w", err)
    }
    // 2. Then the row lock itself, as before.
    a, err := scanAccount(q.db.QueryRow(ctx,
        `SELECT `+accountColumns+
        ` FROM ledger.accounts WHERE id = $1 `+
        lock, id))
    return a, wrapRead("lock account", err)
}
```

Now, once a freeze is waiting, payments that arrive after it queue *behind* it. When it gets through, they see `FROZEN`. The lock order doesn't change, because the advisory lock is taken right before the account row lock, in the same step.

The test is `TestFreezeIsNotStarvedByLaterTx2s`, and it plays out the door scenario:

1. One payment holds the account.
2. A freeze arrives and waits.
3. A second payment arrives after the freeze.
4. Check that the second payment doesn't run first, and that when it does run, it fails with `account_frozen`.

The lesson for me wasn't about Postgres. It was that "the database handles locking" is a sentence that hides a lot of detail. I knew every rule in the design, and none of them said anything about fairness.

## When it broke: the fraud engine's own ticket

In Part 1 I promised that the fraud engine tripped over the very idempotency rules this post praises. Here's how.

The fraud engine watches every settled transaction. One of its rules: more than 3 top-ups in 5 minutes freezes the account. When the rule fires, the engine calls the freeze endpoint, and like every other caller, it sends an idempotency key. The fraud engine can see the same event more than once (Part 5 explains why), and a repeated decision must not mean a repeated freeze.

The key was built from what identifies the decision:

```
fraud:<rule>:<account_id>:<window_start>
```

Good so far. The same rule firing for the same account and the same time window gives the same key. But the **body** of the freeze request included a reason with the running count, like `topup_velocity: 4 top-ups in 3m0s`.

Now play it forward. Top-up number 4 fires the rule: key `K`, reason "4 top-ups in 3m0s." The account is frozen. But credits are still allowed on a frozen account, so top-up number 5 arrives, falls in the same window, and fires the rule again: same key `K`, reason "5 top-ups in ...".

Same key, different request. That's the fourth row of the table: `422 idempotency_key_reused`. The ledger was doing exactly what it should. The fraud engine logged it as a rejected freeze and paged someone, for an account that had been frozen correctly the whole time.

The fix was a rule I now apply everywhere: **the body may only contain what the key already encodes.** The reason became `topup_velocity: window from <window_start>`, built from the same fields as the key. Every later decision for that window sends the identical request, and the ledger replays the original reply. The count moved into the engine's own log line, where it's still useful and can't break anything.

A key is a promise that the request will be identical. Anything in the body that can change breaks that promise.

## The honest costs

None of this is free.

- **Every write does an extra insert.** The key table is real data. In the 30-minute load test, 1.09 million requests left the idempotency table at **896 MB**. Keys expire after 24 hours and a background job deletes them in batches. That means a retry more than 24 hours late is treated as a new request, a limit every client needs to know about.
- **Waiting in line caps how fast one account can go.** Payments on the same ledger run one at a time. That's the point, but it means a single very busy account, like a merchant settlement account, is limited by how fast one row can be locked, updated and committed. The load test ran 10 "hot" accounts at 20 writes a second each, about 36,000 postings per account, and the reconciler found every one consistent afterwards. But it's a real ceiling, and spreading one account's traffic across several ledgers is a design change, not a setting.
- **Clients have to do their part.** The ledger can only recognise a retry if the caller reuses the key. A client that makes a new key on every attempt gets none of this protection, and nothing on the server can fix that.
- **The rules are subtle.** Both bugs in this post came from code that followed the design. The design just hadn't said enough.

## Questions worth asking your engineers

- **"If a customer's retry arrives after the first attempt already succeeded, what do they get?"** The original answer, not a second payment.
- **"Who creates the idempotency key, and when?"** The client, before the first attempt.
- **"What happens if the same key comes back with a different amount?"** It's refused, and someone looks into why.
- **"Can two payments both pass the balance check at the same time?"** No. They wait in line on the ledger row, and a test fires hundreds at once to prove it.
- **"Can the fraud freeze be delayed by the very traffic it's trying to stop?"** Not any more.
