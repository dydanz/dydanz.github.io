*Part 5 of **Money Doesn't Retry: Building a Ledger That Can't Lie**: synchronous and asynchronous work, or how a ledger tells the rest of the world what happened without lying about it.*

---

Rina's top-up went through. After four posts, we know a lot about the moment it did: two journal lines, a new balance, a `TransactionSettled` event, a stored reply for her idempotency key, all in one commit.

But the ledger isn't the only system that cares. Within a second or two, several other things should happen:

- the fraud engine should count it as one of her top-ups in the last 5 minutes
- her phone should get a "Top-up successful" notification
- the analytics team's dashboard should go up by Rp100,000
- the support tool should show it if she calls in

None of those systems live inside the ledger's database. They hear about things through a message stream (in this project, Kafka). So the ledger has to *send a message* about every change.

That sounds like the easy part. It turned out to be the part with the most traps.

---

## Two kinds of work

Think about paying at a restaurant.

Some things have to happen before the waiter tells you "you're all set": the card terminal approves the charge, and the restaurant records that table 12 has paid. If either of those hasn't happened, "you're all set" is a lie.

Other things can happen after you've left: the receipt gets emailed, the day's takings get totalled, the stock system notes that the last slice of cake is gone. If the email arrives a minute late, nobody is harmed. If it never arrives, someone should notice, but your meal is still paid for.

A ledger draws the same line, and it draws it strictly:

| Must happen before "done" | Can happen a moment later |
| :--- | :--- |
| Journal lines written | Fraud engine evaluates it |
| Balance updated | Push notification sent |
| Event recorded | Analytics updated |
| Idempotency reply stored | Search and support tools updated |

The rule for the left column: **anything Rina's "done" is a promise about must be in the same commit.** Part 3 put all of it in one Postgres transaction, Tx2, so it either all happens or none of it does.

The rule for the right column is the subject of this post: it can happen later, but it **must happen**, exactly as recorded, and never for something that didn't.

---

## The two-letter problem

Here's the obvious way to do it. Commit the transaction, then send the message:

```
1. COMMIT the top-up to Postgres
2. send "TransactionSettled" to Kafka
```

Now crash the program between step 1 and step 2. That happens: a deploy, a killed container, a network blip to Kafka. The top-up is committed and the message is never sent. The fraud engine never counts it. Rina's phone never buzzes. The ledger and everything downstream now disagree, and nothing will ever fix it, because nothing remembers that a message was owed.

So flip it. Send first, then commit:

```
1. send "TransactionSettled" to Kafka
2. COMMIT the top-up to Postgres
```

Crash between them, or have the commit fail, and now the fraud engine has heard about a top-up that never happened. Rina gets a "Top-up successful" notification for money she doesn't have. That's worse.

This is called the **dual-write problem**. Two systems, two writes, and no way to make them happen together. A Postgres commit and a Kafka write can't be one atomic step, however carefully you order them.

---

## The outbox tray

An old office has an answer to this.

A clerk updates the ledger book. On the same desk sits an **outbox tray**. Whenever the clerk writes an entry that someone else needs to know about, they write the letter *at the same time*, in the same sitting, and drop it in the tray. The clerk never walks to the post office.

A courier comes by the desk regularly, picks up everything in the tray, takes it to the post office, and ticks each letter off once it's been handed over.

Now look at the failures again:

- **The clerk gets interrupted mid-entry.** The entry and the letter were written together, so either both exist or neither does. No ghost letters, no missing ones.
- **The courier is late, or the post office is closed.** The letters wait in the tray. Nothing is lost. They go out when the courier can get through.
- **The courier hands a stack over and gets interrupted before ticking it off.** Next round, they take the same letters again. Some get posted twice.

That last one is the price, and I'll come back to it. But the first two problems are gone, and they were the dangerous ones.

The trick is that the "letter" is written **into the same database, in the same commit**, as the change it describes. That turns two writes to two systems into one write to one system, plus a delivery job that can be retried forever.

---

## How it's built

### The tray is a table

```sql
CREATE TABLE ledger.outbox (
  id           BIGINT GENERATED ALWAYS
               AS IDENTITY PRIMARY KEY,
  event_id     UUID  NOT NULL UNIQUE,
  topic        TEXT  NOT NULL,
  msg_key      TEXT  NOT NULL, -- account_id
  payload      JSONB NOT NULL,
  headers      JSONB NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL
               DEFAULT now(),
  published_at TIMESTAMPTZ   -- NULL: in tray
);
```

There's one rule in the code that makes this safe: the function that records an event, `AppendEvent`, writes the `events` row **and** its `outbox` row, in the same transaction, every time. There's no other way to record an event. So no state change can be committed without its letter being in the tray.

Unlike the journal and the events from Parts 2 and 3, this table is *not* ledger data. It's operational, like the idempotency keys. Rows get ticked off and, after 3 days, deleted.

### The courier is the relay

A background process, the **relay**, does the courier's job. Stripped of logging, its core is short:

```go
for {
    batch := store.Unpublished(ctx, 500)
    if len(batch) == 0 {
        return
    }
    err := pub.Publish(pctx, records(batch))
    if err != nil {
        return // retry the whole batch
    }
    // A crash here re-publishes the batch:
    // consumers deduplicate on event_id.
    store.MarkPublished(ctx, ids(batch))
}
```

`Unpublished` is `SELECT ... WHERE published_at IS NULL ORDER BY id LIMIT 500`. `Publish` waits until Kafka confirms the messages are stored on its replicas (`acks=all`). Only then does `MarkPublished` set `published_at`. A failed batch is never skipped: it stays in the tray and is tried again, with a growing pause, until it goes through.

Only one relay runs at a time. Several copies of the worker are running, but the relay job is held by whichever one has a Postgres lock called `ledger_outbox_relay`. If that copy dies, another takes the lock and carries on from whatever is still unpublished. (Part 6 is about how that handover works, and how it went wrong.)

### Keeping the order

Messages for one account must arrive in order. A fraud rule that sees a `TransactionSettled` before the `TransactionRequested` for the same payment would be confused, and so would anyone rebuilding Rina's history from the stream.

Two things preserve the order:

1. **The outbox ids are in commit order for each account.** Part 4's row lock means two payments on Rina's ledger run one at a time, and each writes its outbox rows while holding the lock. So her rows' ids line up with the order her payments committed in.
2. **Kafka keeps one account's messages together.** Every message is keyed by `account_id`, so all of Rina's events land on the same partition, which Kafka delivers in order.

And as a last check, every message carries its `stream_id` and `stream_version` from Part 3. A consumer can always tell if it's looking at version 3 before version 2.

## "Exactly once", honestly

Back to the courier who got interrupted before ticking off the stack.

If the relay crashes after Kafka has the messages but before `MarkPublished` commits, the next relay sends the same batch again. That's not a bug. It's the deal. The outbox guarantees **at-least-once** delivery: every message gets out, and some get out twice.

You'll see systems advertise "exactly-once delivery." Between a database and a message broker, that isn't on offer, for the same reason as the dual-write problem. What you can build is **effectively-once processing**: deliver at least once, and make every consumer ignore what it has already seen.

The fraud engine does this with Redis:

```
SET fraud:seen:<event_id> 1 NX EX 604800
```

`NX` means "only if it isn't already there." The engine checks for the mark before evaluating an event, and sets it only **after** the event is fully handled. If the engine crashes between freezing an account and setting the mark, it sees the event again and sends the freeze again, which Part 4's idempotency keys turn into a harmless replay. Setting the mark first would be the other mistake: a crash would leave the event marked as seen but never handled, and a freeze would be lost.

This is the "Part 5 explains why" from Part 4. The fraud engine sees repeated events because delivery is at-least-once, by design. Its freeze key had to be stable because of that.

The ledger itself, the thing that holds the money, is still exactly-once. That's Part 4's job, and it's done inside Postgres. Only the notifications *about* the money can repeat.

## What "later" costs

Putting fraud detection on the right side of the table has a cost, and it's worth saying plainly.

The fraud engine freezes Rina's account only after it hears about her 4th top-up. Between that top-up committing and the freeze committing, the relay has to wake up, Kafka has to deliver, the engine has to evaluate and call the ledger. A debit that settles inside that gap goes through.

The target for that gap is **under 2 seconds at p99**. In the integration test, commit to freeze took about **22 ms**. Any debits that do slip through are recorded in the `AccountFrozen` event's audit context, so they can be found.

Could the fraud check go on the left side instead, inside the payment? Then every payment waits for fraud rules to run, a slow fraud engine slows every payment, and a broken fraud engine stops every payment. For this system, a short and *measured* window was the better trade. But it's a trade, and the people who own fraud risk should be the ones to agree to it.

## When it broke: the doorbell

The courier has to know when to come by. Checking the tray every 200 ms works, but most of the time the tray is empty, and a new letter waits up to 200 ms for nothing.

Postgres has a built-in doorbell for this: `LISTEN` and `NOTIFY`. The relay listens on a channel called `ledger_outbox`, and anyone can ring it. So my first version rang the bell inside every payment transaction, right after writing its outbox rows. Commit, the bell rings, the relay wakes up instantly. Neat.

Then I ran the load test at 500 payments a second, and every run had a p99 of **302 to 397 ms**, against a target of 150.

The database's own wait statistics showed it: up to **30 connections** stuck waiting on `Lock:object`, behind one holder. Looking at the lock table, the object was the database itself.

Here's what I hadn't known. A Postgres transaction that calls `NOTIFY` takes a **database-wide lock when it commits**, and it holds that lock through the commit's flush to disk. So every payment, at the moment it committed, queued behind every other payment's commit. Part 4 worked hard to make payments on *different* accounts run side by side. The doorbell put them all back in a single line.

Picture a building where every clerk must hold the one bell rope while their ink dries.

The fix was to take the doorbell out of the payment. Each server process now has a small **notifier**. After a commit that wrote outbox rows, the code asks the notifier to ring, and the notifier rings at most once every 10 ms, on its own, outside any payment:

```go
// Notify asks Run to send a NOTIFY. It never
// blocks; calls that arrive while one is
// pending are merged into it.
func (n *Notifier) Notify() {
    if n == nil {
        return
    }
    select {
    case n.wake <- struct{}{}:
    default:
    }
}
```

`Run` loops: wait for a request, send one `pg_notify`, sleep 10 ms. A burst of a thousand commits costs one bell. That bell's transaction writes nothing to disk, so it holds the database lock only for a moment.

The results:

- the `Lock:object` waits disappeared
- p99 in the quick load profile fell to **63 to 112 ms** in two of three runs
- the cost was about **6 ms** of extra outbox delay at p50

And if the bell fails altogether, nothing is lost. The relay still checks the tray every 200 ms, so a broken doorbell costs latency, not letters.

What I took from it: "wake up the consumer" felt like a side effect, not a write, so I put it inside the payment without thinking. Anything inside the payment's commit is on the payment's critical path. The doorbell belonged on the right side of the table all along.

## When it broke: the courier who stopped reporting

The chaos drill for this part is simple: stop Kafka for 5 minutes while payments keep coming, then start it again.

The outbox did exactly its job:

- **21,101 of 21,101** writes during the outage were answered on the first try, with latency unchanged
- the tray grew to **46,320** unsent rows
- it drained **9 seconds** after Kafka came back
- **0 of 63,503** events were lost, and **458** were delivered twice

Those 458 are the courier repeating a stack, 0.7%, and the fraud engine skipped every one of them.

So the money was fine. What wasn't fine was what I could *see*.

The relay logs an `outbox.lag` line every 30 seconds, saying how many letters are waiting and how old the oldest is. An alert fires when the lag is over 5 seconds for 2 minutes. During the outage, those lines stopped. The alert eventually fired, 4.5 minutes in, through its "no heartbeat" path, and its message said the relay wasn't running. The relay was running. Kafka was down.

The cause: the relay sends each batch with a 10-second deadline. The first batch failed straight away. The next batch of 500 called `Publish`, and `Publish` didn't come back for **296 seconds**, until Kafka was back. The Kafka client library retries delivery indefinitely by default, and my wrapper waited for it instead of returning at the deadline. And because the relay wrote its lag line from the same loop, a stuck publish meant no lag line.

Two fixes:

1. **`Publish` returns at its deadline.** It leaves the stuck records in flight, and until they settle it sends nothing new. So however often the relay retries, an outage costs at most one extra copy of one batch.
2. **The lag report runs on its own.** It has its own goroutine and its own timer, so a stuck publish can't silence it.

Re-running the same drill:

| | Before | After |
| :--- | :--- | :--- |
| `outbox.lag` during the outage | none | every 30 s, up to 287,606 ms |
| Alert Pending | 2.5 min (on no data) | 33 s (on the lag value) |
| Alert firing | 4.5 min | 2 min 33 s |

Both fixes have tests that fail on the old code. One uses a fake Kafka broker that accepts a request and never answers, which reproduces the stall with the real client library.

Nothing was lost before the fix either. But "it's still working" and "I can see that it's still working" are different claims, and an alert that blames the wrong component sends the on-call engineer the wrong way, during the 5 minutes that matter.

## The honest costs

- **Every event is written twice.** Once in `events`, once in `outbox`. More disk, more WAL, a purge job, and one more table to keep healthy.
- **"A moment later" has a size, and it's not tiny.** The target is outbox lag under 1 second at p99. In the 30-minute load test at 500 writes a second, it was **980 ms** at p99 and **2.5 s** at worst. Met, barely, on a laptop disk.
- **Every consumer must deduplicate.** At-least-once is a promise to the producer, but it's work for every team that reads the stream. A consumer that doesn't dedupe will double-count, and the outbox can't stop it.
- **The fraud window is real.** A short gap between a suspicious payment and the freeze, measured and logged, but not zero.
- **The stream isn't the archive.** Kafka keeps messages for 7 days. The permanent record is the event table in Postgres, from Part 3. Anyone who needs history older than a week reads it there.

---

## Questions worth asking your engineers

- **"If the app crashes right after a payment commits, does the fraud system still hear about it?"** Yes, because the message was committed with the payment and waits in the outbox.
- **"Can a downstream system ever hear about a payment that didn't happen?"** No. The message only exists if the payment committed.
- **"Can it hear about one twice?"** Yes. Every consumer must ignore repeats. Ask which ones do.
- **"How long between a payment and the fraud check, and who agreed to that gap?"** There should be a number, and an owner.
- **"If the message broker goes down, how long until someone knows, and does the alert say why?"**
