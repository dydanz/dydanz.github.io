*Part 3 of **Money Doesn't Retry: Building a Ledger That Can't Lie**: event sourcing, or why the ledger remembers every step and not just the result.*

---

Back to the tunnel.

In Part 1, Rina tapped **Top up**, lost her signal, and got "Something went wrong." In Part 2 we saw the journal: the ink-only record of money that actually moved.

But think about what the journal can tell her support agent about that *first* tap. If the top-up never completed, there's nothing in the journal at all. No line, no amount, no balance change. The journal is silent.

Silence isn't an answer. "Nothing happened" and "your request arrived, and we were halfway through it when the connection dropped" are very different stories, and the support agent needs to know which one it was. So does the system itself, because if it's the second story, someone has to finish the job.

That's what this post is about: the second kind of record, the one that remembers *every step*, not just the money.

---

## How a parcel tracker thinks

Order something online and open the tracking page. You'll see something like:

> - **Mon 09:12** Order placed
> - **Mon 14:40** Picked up by courier
> - **Tue 06:03** Arrived at sorting center
> - **Tue 08:55** Out for delivery
> - **Tue 11:21** Delivered

The page also shows a big status at the top: **Delivered**. But that status isn't really stored anywhere as the truth. It's just the *last scan*. The truth is the list of scans: who touched the parcel, where and when.

That design has some lovely properties:

- If the status at the top ever looks wrong, you can work it out again from the scans.
- If a parcel goes missing, you know exactly where it was last seen, and by whom.
- If two people disagree about what happened, the scans settle it.

**Event sourcing** is the same idea applied to software. Instead of storing "Rina's top-up: SETTLED" as a value that gets overwritten, the system stores every step as an **event** that's never changed or deleted, the same way the journal is written in ink. The current state is whatever you get by replaying those events in order.

Programmers call that replay a *left-fold*: start from nothing and apply each event in turn. You can just think of it as reading the story from the beginning.

## The life of a transaction

In this ledger, every credit, debit and void goes through the same short story, and every step is an event:

```
request
   |
   v
PENDING           "we've got it, and it's saved"
   |
   v
PROCESSING        "checking the balance and the rules"
   |
   +----------->  FAILED     checks failed, or timed out
   |
   v
SETTLED           "done, the money moved"
   |
   |  a later void of this transaction settles
   v
VOIDED            "settled, then reversed"
```

In plain words:

| State | What it means | The event that gets you there |
| :--- | :--- | :--- |
| **PENDING** | "We've got your request, and it's safely saved." | `TransactionRequested` |
| **PROCESSING** | "We're checking the balance and the account." | `TransactionProcessing` |
| **SETTLED** | "Done. The money moved, and it's in the journal." | `TransactionSettled` |
| **FAILED** | "We checked, and it can't happen." For example, not enough money, or the account is frozen. | `TransactionFailed` |
| **VOIDED** | "This one was settled, and later reversed." | `TransactionVoided` |

Three rules make the story trustworthy:

- **Only the arrows above are allowed.** A transaction can't jump from PENDING straight to SETTLED, can't come back from FAILED, and can't be voided twice. Anything else is rejected as an illegal transition, by the code *and* by the auditor that re-checks it later.
- **FAILED is final.** If Rina's purchase fails for lack of funds, retrying the same request gets the same answer. Trying again for real is a *new* request (Part 4 explains how the system tells those apart).
- **A void doesn't rewrite the original.** It's a separate transaction with its own PENDING → SETTLED story, and when it settles, it adds one more event to the original's story: `TransactionVoided`. The original's history is untouched; it just gets a new last chapter.

Accounts have stories too: `AccountOpened`, `LedgerOpened`, `AccountFrozen` and `AccountUnfrozen`. Each freeze event records *why* and *who*: the reason, the actor, and for automatic freezes, which fraud rule fired. When a customer asks "why can't I pay?", the answer is a lookup, not an archaeology project.

## Why "saved" comes before "processed"

Here's a detail that turns out to be the key to Rina's tunnel.

The ledger handles every request in **two separate database transactions**:

```
Tx1  (short)
  record the request: transaction = PENDING, event TransactionRequested
COMMIT   ← from here on, the request can't be lost

Tx2  (under locks)
  append TransactionProcessing
  check the balance, the account status, the rules
  append TransactionSettled + write the two journal lines   (or TransactionFailed)
COMMIT
```

The first step is tiny: write down "this request exists." Once it commits, the request is durable. A crash, a dropped connection or a database restart can't make it disappear.

The second step does the real work, and it writes PROCESSING *and* the final outcome in the same commit. That means a transaction can never be left sitting in PROCESSING. It's either PENDING (saved, not yet worked on) or finished.

That gives the system a very simple recovery signal: **a transaction that's been PENDING for more than five seconds was interrupted.** A background job, the *sweeper*, looks for exactly those and runs the second step for them. If one stays stuck for 15 minutes, it's moved to FAILED with the reason `processing_timeout`, still through PROCESSING, so even the failure follows the rules.

Remember the one write in Part 1's database-kill drill that got a `202` ("accepted, still working on it")? That was a transaction caught between Tx1 and Tx2: saved, but not yet processed, when the database died. After recovery, the sweeper found it in PENDING and finished it. The event stream recorded every step, including that a recovery job did the finishing.

Without the events, that transaction would have been invisible: no journal line, no balance change. With them, it was a story with an obvious missing chapter, and something whose job it was to write it.

## The code: a story with rules

The state machine lives in a small Go package with one important property: **it does no I/O.** No database, no network, no clock. It takes the current state and an event, and returns the next state or an error:

```go
// ApplyTransaction returns s with e applied, enforcing the state machine:
//
//	(none) -Requested-> PENDING -Processing-> PROCESSING -Settled-> SETTLED -Voided-> VOIDED
//	                                                      `-Failed-> FAILED
func ApplyTransaction(s Transaction, e Event) (Transaction, error) {
	if e.StreamVersion != s.Version+1 {
		return s, fmt.Errorf("%w: have %d, got %d", ErrVersionMismatch, s.Version, e.StreamVersion)
	}
	illegal := func() (Transaction, error) {
		return s, fmt.Errorf("%w: %s in state %q", ErrIllegalTransition, e.Type(), s.Status)
	}
	next := s
	switch p := e.Payload.(type) {
	case TransactionSettled:
		if s.Status != StatusProcessing {
			return illegal()
		}
		next.Status, next.LedgerSequence, next.BalanceAfter = StatusSettled, p.LedgerSequence, p.BalanceAfter
	case TransactionVoided:
		if s.Status != StatusSettled || s.Type == Void {
			return illegal()
		}
		next.Status, next.VoidedBy = StatusVoided, p.VoidTransactionID
	// ... Requested, Processing, Failed follow the same pattern
	}
	next.Version = e.StreamVersion
	return next, nil
}

// FoldTransaction is the left-fold of a transaction stream, in version order.
func FoldTransaction(events []Event) (Transaction, error) {
	var s Transaction
	for _, e := range events {
		var err error
		if s, err = ApplyTransaction(s, e); err != nil {
			return s, err
		}
	}
	return s, nil
}
```

Two things to notice:

- **Every event carries a version number**, and each one must be exactly the previous version plus one. Events can't be skipped, duplicated or applied out of order without the fold refusing them. In the database, `(stream_id, stream_version)` is unique, and versions are assigned while holding the stream's row lock.
- **The same function runs everywhere.** The request path uses it to move a transaction forward. The auditor (the reconciler, Part 6) uses it to re-derive every transaction from its events and compare. One definition of "what the story means," used by both sides.

The business decision is pure too. Given what Tx2 read under its locks, `Decide` returns *settle* or *fail, and why*, in a fixed order:

```go
// Decide applies the business rules in TRD §7.1, in order:
//
//	ledger missing                         → FAILED ledger_not_found
//	VOID of anything but a SETTLED non-void → FAILED not_voidable
//	DEBIT on a FROZEN account              → FAILED account_frozen
//	result below −overdraft_limit          → FAILED insufficient_funds (also for voids, TRD §16 Q3)
//
// Credits settle on frozen accounts (FR-09), and voids are allowed on frozen
// accounts (Q3 default). An int64 overflow is an error, not a business failure.
```

Keeping the rules free of I/O made them cheap to test hard, and that's where the next part comes in.

## A robot that lives thousands of random banking days

The domain package has a **property test**: instead of checking a handful of hand-picked examples, it generates thousands of random sequences of credits, debits, voids and freeze toggles against one ledger, pushes each through `Decide` and the state machine exactly as Tx2 would, and checks that a set of rules holds after every step:

- the balance never drops below its floor;
- the balance equals the sum of everything that settled, and every "balance after" equals the running sum at that point;
- replaying each transaction's events gives *exactly* the state that processing produced;
- a transaction is voided at most once, and only from SETTLED.

If you don't write code, think of it as a robot playing thousands of randomly chaotic days at the bank (top up, spend, refund, freeze, refund a refund) and checking the books after every move. Hand-written tests check the cases you thought of. Property tests find the ones you didn't.

## The source of truth, and everything else

If the events are the truth, what about the familiar tables, like a `balance` column or a transaction `status`? They still exist, because reading a balance by replaying years of history on every request would be absurd. But they have a different job, and the design is strict about the difference:

| Kind | Tables | Can it change? | Can it be rebuilt? |
| :--- | :--- | :--- | :--- |
| **Source of truth** | `events`, `journal_entries` | Insert only. Updates and deletes are blocked. | No. This *is* the history. |
| **Projections** | `accounts` (status), `ledgers` (balance), `transactions` (status) | Updated only in the same database transaction as the event they reflect | Yes, by replaying the source of truth |
| **Operational** | `idempotency_keys`, `outbox`, `checkpoints` | Mutable and purged on schedule. Not ledger data. | Not needed |

A **projection** is the parcel tracker's big status label: a convenient summary of the story, kept for fast reads. Because each projection is updated in the *same* commit as the event it reflects, it's never stale. A balance you read is the balance.

The rule that follows is simple and strict: **if a projection and the history disagree, the history wins.** The projection is just a cache with good manners.

## When the summary drifts: rebuild, but carefully

Projections *can* drift: a bug in an update, a manual "fix" someone ran in production, a migration with a mistake in it. The design assumes that will happen eventually and plans for it in two parts.

**First, notice.** Every minute, the reconciler (Part 6 covers it in full) re-folds the event streams of recently changed transactions and accounts and compares the result field by field: status, version, type, amount, currency, account, ledger, failure reason and more. A mismatch is reported as `projection_drift` and pages someone. A stream that can't even be folded (an event that doesn't decode, or an illegal transition) is a mismatch too.

The reconciler **never auto-corrects.** That's deliberate. If the summary and the story disagree, a human should know *why* before anything changes, because the cause might be a bug that's still running.

**Then, repair, deliberately.** The repair tool is `ledger-worker rebuild-projections`, and its defaults are designed for a nervous person at 2 a.m.:

- **Dry run by default.** It recomputes every projection from the source of truth, logs one line per column that differs, and rolls back. Nothing changes unless you add `--apply`.
- **Scoped if you want.** `--account <id>` limits it to one account.
- **Safe while live.** Each row is rebuilt in its own transaction, under the same lock the write path uses, so it can run while the ledger is serving traffic.
- **Clear exit codes.** 0 means nothing differed (or everything was applied), 3 means a dry run found differences, and 1 means a row failed.
- **It can't touch the truth.** It never modifies events or the journal. A gap in the journal or an unbalanced entry can't be "rebuilt" away; that needs a void or a migration reviewed by a human.

That last point is the whole philosophy in one line. **Summaries are disposable. History is not.** You can always regenerate a summary from the history. If you let anyone regenerate the history, you no longer have one.

## Following one request through everything

There's one more thread running through every event: a **trace id**.

When a request arrives, the API accepts the caller's trace id (a standard `traceparent` header) or generates a new one, and echoes it back. That same id is written to the transaction, every one of its events, both journal lines, the outbox row and the Kafka message headers. When the fraud engine reacts to an event and freezes an account, it continues the same trace. When the sweeper finishes a stuck transaction, or the reconciler checks one, they log with the transaction's original trace id.

So when Rina's support ticket arrives, the question "what happened to her top-up?" becomes a single query over the logs or the database, returning the whole story across every service. The web console's transaction screen shows it as a timeline, and each step names its **actor**: the client that requested it, the recovery job that finished it, the outbox relay that published it, the fraud engine that reacted to it, the reconciler that checked it.

For Rina's tunnel, the answer looks something like this (an illustration, not a real record):

> - **08:12:03.114** Requested, by the payments client
> - **08:12:03.120** Processing
> - **08:12:03.131** Settled: +100,000, balance after 250,000
> - **08:12:03.390** Published to the event stream
> - **08:12:09.502** Same key received again: original response replayed

The second tap didn't create a second top-up. It got back the answer to the first one. *How* the system knew to do that is the subject of the next post.

## The honest costs

Event sourcing isn't free, and I'd be doing you a disservice if this post read like a sales pitch.

- **You write things more than once.** Each write stores its events, and a copy of each event goes into an outbox for publishing (Part 5). The load test measured about **11 KB of database log (WAL) per write**, and the outbox was the largest table in the database at 3.7 GB after a long run. There are known ways to slim that down; I haven't picked one yet.
- **Events are forever, so their shape is too.** Every event carries a `schema_version`. When the fraud engine needed the type, amount and currency on `TransactionSettled`, those fields were added within version 1, *additively*, so old events still fold. Renaming or removing a field means a new version, and code that understands both forever.
- **Stories get long.** Replaying ten years of events to read a balance would be slow, which is why the projections exist and why archiving (Part 2) writes checkpoints, so a fold can start from a known point instead of from the very first event.
- **Not everything needs it.** The auth service in the same repo isn't event-sourced. It has an append-only audit trail, which is enough for logins. Use event sourcing where the history *is* the product (money, in this case), not everywhere.

## Questions worth asking your engineers

- **"If a payment never completed, can we see how far it got?"** Yes: every step is recorded, including the ones before any money moved.
- **"What happens to a request that was interrupted halfway?"** Something finds it automatically and either finishes it or fails it with a clear reason.
- **"If the balance shown and the history disagree, which one wins?"** The history, always. And something checks for disagreements continuously.
- **"Can we rebuild the summaries without touching the history?"** Yes, with a dry run first.
- **"Can support follow one request across every system with a single id?"** Yes.
